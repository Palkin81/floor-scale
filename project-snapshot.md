# СОСТОЯНИЕ ПРОЕКТА

**Цель:** Два ESP-устройства с общей логикой настройки сети без Home Assistant на этом этапе. Весы (XIAO ESP32-C6, HX711, измерение и калибровка по кривой) и экран (generic ESP32, пока заглушка со страницей настройки, позже дисплей). Настроил одно, настроились оба: пользователь вводит домашнюю сеть на странице одного устройства, оно шифрует креды AES-256-GCM и передаёт соседу по HTTP. Оба переходят в домашнюю сеть. Шифрование ключом `espectre_encryption_key`, тем же, что для API и OTA.

**Текущий этап:** Этап 4–5, устранение нестабильности после сброса и проверка передачи Wi‑Fi по воздуху. Выбор ролей работает правильно: экран — AP/мастер, C6 — STA/слейв. Но обмен не завершён: экран всё ещё пытается подключиться к пустому SSID, C6 многократно теряет AP, а запросы к `192.168.4.11/prov` иногда получают HTTP 404. Это означает, что TCP/HTTP-сервер на `.11` отвечает, но нужный маршрут не найден (либо на `.11` работает не та прошивка/не то устройство). Последний лог не подтверждает успешную передачу.

По запросу добавлен в веб-морды статус роли и связи между устройствами. Реализация готова в коде, но не собрана и не проверена на железе.

## Уже сделано

- **Весы:** чтение HX711 (D10/D9, 10 Гц, RATE на GND), медиана и EMA, машина состояний IDLE → WAIT_STABLE → RESULT, адаптивный допуск стабильности, таймер выключения дисплея 10 с, калибровка по кривой до 5 точек, ноль при загрузке с проверкой, кнопки «Обнулить», «Калибровать», «Сбросить точки», OTA с шифрованием.
- **Экран:** страница на порту 80, поиск сетей через событие ESP-IDF, проверка пароля, сброс сети, окно настройки 5 минут, приём `POST /prov` и отправка соседу после проверки пароля.
- **Весы:** та же страница и сетевая логика, плюс блоки веса и калибровки. Пользователь собрал и прошил весы; поиск и подключение к сети работают без ошибок. В этой проверке датчик не подключался, ранее его проверяли отдельно.
- Сквозная проверка экран → весы прошла: экран AP `192.168.4.11`, весы получили STA IP `192.168.4.111`; после подтверждённого POST оба перезагрузились и подключились к `Xiaomi_1F6A` (экран `192.168.31.179`, весы `192.168.31.112`, на момент проверки).
- Добавлен каскадный сброс Wi-Fi: экран ищет весы по mDNS в домашней сети; в setup-сети используются AP/STA IP. Первая аппаратная попытка сброса не получила HTTP-ответ от весов (`ESP_ERR_HTTP_EAGAIN`). Установлено также, что `WiFiComponent::clear_sta()` очищает только список сетей в RAM, а не сохранённые credentials; это подтверждено повторным подключением экрана к `Xiaomi_1F6A` после сброса.
- Первый вариант очистки preference сохранял пустую запись: это удаляло домашнюю сеть, но ESPHome загружал её как STA с пустым SSID. Исправлен подход: стереть только NVS-ключ Wi-Fi `88491487` из namespace `esphome`, затем очистить STA-драйвер и перезагрузить. Это должно сохранить остальные preferences, включая калибровку. Новый вариант ещё не собран и не проверен на железе.
- В последнем логе экрана mDNS-запрос `floor-scale` завершился `ESP_ERR_NOT_FOUND`, поэтому `/peer_reset` к весам не отправлялся. Экран очистил свою сеть (`preference=ok`, `sync=ok`, `driver=ESP_OK` в старой реализации) и перезагрузился. Для выяснения причины нужен лог весов за тот же период: были ли они в домашней сети, получили ли IP и запущен ли HTTP UI.
- В проверенной передаче экран сначала получил timeout при попытке `192.168.4.110`, затем успешно доставил блок весам на `192.168.4.111`; это похоже на перебор IP телефона перед STA-клиентом.
- `probe::try_connect` временно ставит тестовую сеть с `WIFI_STORAGE_RAM`, затем восстанавливает сохранённую STA-конфигурацию и `WIFI_STORAGE_FLASH`. В этой версии IDF нет `esp_wifi_get_storage`; используется документированное значение по умолчанию FLASH.
- Ранее `floor-screen.local` открывался, `floor-scale.local` — нет. После перехода обоих в домашнюю сеть проверить mDNS повторно; на момент теста доступны IP `192.168.31.179` (экран) и `192.168.31.112` (весы).
- Исправлен выбор роли: `netrole::find_bssid` переводит AP в APSTA перед сканированием и исключает собственный BSSID. Сквозной сценарий экран → весы проверен.
- Добавлены INFO-логи AP/STA: режим, MAC/BSSID, канал, найденные сети, решение по MAC, подключение/отключение с reason code и выданный STA IP. Пароли не логируются. В логах остаётся предупреждение `esp_wifi_scan_get_ap_record failed: ESP_FAIL` после чтения результатов обработчиком; сканирование при этом сообщает fetched=10 и передача проходит.
- `lib/prov_link.h` отправляет сформированный `prov::encrypt` блок на `/prov`: к клиенту точки — по адресу из DHCP-списка, к точке соседа — по фиксированному адресу. Сосед сохраняет сеть только при открытом окне.
- В `lib/ui_server.h` добавлены UI-поля «Режим пары» и «Связь с устройством». Локальная роль показывается как «Точка доступа (мастер)», «Клиент (слейв)», «Домашняя сеть» или «Ожидание сети». Проверка связи подтверждает вид второго устройства через `/peer_identity`: AP перебирает DHCP-клиентов, STA использует IP AP соседа, в домашней сети применяется mDNS. Фоновый монитор проверяет AP/STA каждые 5 секунд, домашнюю сеть — раз в 30 секунд; `/status` читает кэш, чтобы не блокировать HTTP-сервер.
- По новым логам обнаружена гонка старта ролей: `pick_role` сканировал только один раз, до запуска AP соседа. Теперь обе конфигурации повторяют поиск раз в 10 секунд, пока не появится сохранённая сеть или AP партнёра; при обнаружении MAC-правило по-прежнему выбирает одного мастером, второго слейвом.
- В проверке статуса мастера добавлен 15-секундный отрицательный кэш по MAC неизвестных DHCP-клиентов, чтобы телефон не вызывал HTTP timeout на каждом цикле мониторинга.
- Последние логи подтвердили MAC-выбор ролей: экран BSSID `3C:71:BF:AA:D3:B9` остался AP; C6 BSSID `CC:8D:A2:F3:E2:B1` выбрал STA. C6 смог получить `192.168.4.110`, но экранные попытки подключения к `SSID ""` перезапускают адаптер и рвут соединение. На экране, вероятно, осталась пустая preference от старой прошивки; новый reset callback её удаляет, но после сборки с ним нужно выполнить сброс сети.
- В `probe::try_connect` добавлено ожидание восстановления прежней сети до получения IP (до 10 с), а не только ассоциации. Если соединение/IP не восстановились, POST `/prov` соседу не отправляется и UI возвращает понятное сообщение.
- Последние аппаратные логи (20:14–20:23, прошивки около 19:55) уточнили проблему: экран `3C:71:BF:AA:D3:B9` выбирается AP, C6 `CC:8D:A2:F3:E2:B1` выбирается STA. C6 временами подключается к экрану и получает `192.168.4.110`, gateway `192.168.4.11`, но затем связь рвётся и повторяется.
- В этих же логах C6 неоднократно отправляет `POST http://192.168.4.11/prov` и получает `err=ESP_OK http=404 accepted=no`. Это не сетевой timeout: HTTP-узел отвечает, но путь `/prov` не обслуживается на доступном сервере либо на `.11` прошита/запущена не та сборка. Нужно проверить, что `.11` действительно экран с актуальной прошивкой и что в его HTTP-сервере зарегистрирован `POST /prov`.
- Экран продолжает попытки подключения к пустому SSID: `Connecting to ''`, `ESP_ERR_WIFI_SSID`, таймауты и перезапуски Wi‑Fi. В этом сеансе нет подтверждения запуска нового сброса, который стирает NVS preference `88491487`; поэтому старая пустая preference, вероятно, всё ещё сохранена. После проверки актуальной прошивки выполнить сброс сети на экране и проверить `preference_erase=ok` и отсутствие подключения к `''`.
- Добавленная защита в `probe::try_connect` иногда пишет `previous network not restored with IP; skipping peer send`; это предотвращает отправку кредов, пока C6 не вернулся в setup-сеть. Но повторные проверки Wi‑Fi и сканирования совпадают с периодами разрыва и не позволяют считать канал связи стабильным.
- Все `id`, `name`, `friendly_name` латиницей без пробелов (проверено скриптом). Русский только в сообщениях и на странице.
- `lib/ui_server.h`: команды калибровки ставятся в очередь (`cmd_pending`) и выполняются в цикле датчика (`run_pending()`). Статус хранится в фиксированном буфере `status_buf`. Сделано после обнаружения риска падения из-за доступа к состоянию из двух задач.
- Архив `esphome-project.zip` в структуре `/config/esphome`.

## Ключевые решения и ограничения

- Общая сеть настройки `prov_ssid`, пароль `prov_password`. Ненастроенное устройство сначала проверяет сохранённую сеть, затем ищет `prov_ssid` без подключения. При обнаружении AP устройство с большим MAC становится клиентом, меньшее остаётся AP. Перед решением случайная задержка 0–10 с, в `script`, не в `on_boot`.
- Точки доступа в согласованной схеме: экран `192.168.4.11`, весы `192.168.4.10`, одна подсеть `192.168.4.0/24`. В проверенном сценарии экран был AP, весы STA-клиентом.
- Страница встроена в `lib/ui_server.h`. `web_server` ESPHome отключён, css и js не нужны. Порт управления httpd `32769`, стек httpd 12 КБ.
- Сканирование: компонент `wifi` ESPHome забирает результаты раньше нас, поэтому используется обработчик `WIFI_EVENT_SCAN_DONE`. Перед сканированием режим AP переключается в APSTA без подключения, иначе `ESP_FAIL`.
- Приём кредов только при открытом окне. Счётчика версий нет, защита от повтора обеспечивается окном.
- Блок кредов: `nonce(12) | tag(16) | ciphertext`, открытый текст `ssid\npassword`, hex в теле `POST /prov`, до 300 байт. SSID до 32 байт, пароль до 64.
- `include_builtin_idf_components` на верхнем уровне `esp32` ESPHome 2026.10.0 не принимает. Используется `framework: advanced: include_builtin_idf_components: [esp_http_server, esp_http_client]`.
- Задержки в `on_boot` блокируют цикл дольше 5 с и срабатывают watchdog. Задержки только в `script`.
- Имя текущей сети берётся через `esp_wifi_sta_get_ap_info`. `wifi_ssid()` в 2026.10.0 не существует.
- Сквозной сценарий экран → весы проверен; обратный сценарий и работа весовой страницы после перехода в домашнюю сеть ещё не проверены.
- **Проверить:** тестовая сеть не должна сохраняться во флеш; `probe::try_connect` использует `WIFI_STORAGE_RAM` и восстанавливает прежнюю STA-конфигурацию. Проверить на обеих платах.
- Автонуль в покое на весах в текущей версии отсутствует. Решение не принято.
- Гонка за роль точки при одновременном старте не решена полностью.
- Один ключ открывает API, OTA и шифрование кредов.
- Клиентское устройство доступно только по IP в сети другого устройства.
- Проверка пароля через AP+STA: на экране страница не пропадала, но риск остаётся.
- Мобильная вёрстка страницы и список сетей на телефоне не проверены.

## Текущий результат

В текущем репозитории присутствуют `floor-scale.yaml`, `screen_stub.yaml`, `make_blob.py`, `plan.md` и пять заголовков в `lib/`, включая новый `prov_link.h`. Локальные `secrets.yaml` и архивы сборки в репозиторий включать не следует.

### Блок wifi (весы; у экрана адрес `.11`)

```yaml
wifi:
  id: wifi_comp
  ap:
    ssid: ${prov_ssid}
    password: ${prov_password}
    manual_ip:
      static_ip: 192.168.4.10   # экран использует 192.168.4.11
      gateway: 192.168.4.10
      subnet: 255.255.255.0
  on_connect:
    - lambda: |-
        if (prov::is_home_network("${prov_ssid}")) {
          ui::close_window();
          ui::set_status("Подключено к домашней сети");
        }
  reboot_timeout: 15min
```

### Выбор роли (script)

```yaml
script:
  - id: pick_role
    then:
      - delay: !lambda 'return esp_random() % 10000;'
      - lambda: |-
          std::string saved;
          uint8_t found[6] = {0};
          if (netrole::saved_sta(saved)) {
            ESP_LOGI("role", "Saved network %s, keeping it", saved.c_str());
          } else if (netrole::find_bssid("${prov_ssid}", found) &&
                     netrole::should_join_as_client(found)) {
            ESP_LOGI("role", "Setup network found, joining as client");
            id(wifi_comp)->save_wifi_sta("${prov_ssid}", "${prov_password}");
            App.reboot();
          } else {
            ESP_LOGI("role", "No setup network to join, staying as access point");
          }
```

### Инициализация страницы (on_boot, весы)

```yaml
esphome:
  on_boot:
    priority: -100
    then:
      - lambda: |-
          ui::prov_key = "${prov_key_b64}";
          ui::device_kind = "scale";
          ui::device_title = "Весы";
          ui::on_reset = []() {
            const bool cleared = netrole::clear_saved_sta(id(wifi_comp));
            ESP_LOGI("reset", "persistent Wi-Fi credentials cleared=%s", cleared ? "yes" : "no");
            App.reboot();
          };
          ui::on_creds = [](const std::string &ssid, const std::string &pass) {
            id(wifi_comp)->save_wifi_sta(ssid, pass); delay(1000); App.reboot(); };
          ui::wifi_comp_ptr = id(wifi_comp);
          ui::open_window(${window_ms});
          ui::set_status("Окно настройки открыто на 5 минут");
          ui::start(80);
      - script.execute: pick_role
```

Экран то же без `device_kind`, `extra_status` и колбэков калибровки.

### Очередь команд (lib/ui_server.h)

```cpp
inline volatile bool cmd_pending = false;
inline std::string cmd_name;
inline float cmd_known = 0.0f;

inline void run_pending() {
  if (!cmd_pending) return;
  cmd_pending = false;
  std::string r;
  if (cmd_name == "zero" && on_zero) r = on_zero();
  else if (cmd_name == "calib" && on_calib) r = on_calib(cmd_known);
  else if (cmd_name == "curve_reset" && on_curve_reset) r = on_curve_reset();
  if (!r.empty()) set_status(r);
}
```

Вызов в начале `on_value` датчика HX711 весов: `ui::run_pending();`.

### Статус в фиксированном буфере

```cpp
inline char status_buf[160] = "Ожидание";
inline void set_status(const std::string &s) { snprintf(status_buf, sizeof(status_buf), "%s", s.c_str()); }
```

### Приём кредов (POST /prov)

```cpp
static esp_err_t h_prov(httpd_req_t *req) {
  if (!window_open()) { set_status("Окно настройки закрыто. Откройте его кнопкой на странице"); /* ответ */ }
  std::string blob;  // recv_body(req, blob, 300)
  std::string ssid, pass;
  if (!prov::decrypt(prov_key.c_str(), blob, ssid, pass)) { set_status("Ошибка: неверный ключ или данные"); /* ответ */ }
  set_status("Креды приняты, перезагрузка");
  close_window();
  // ответ, затем on_creds(ssid, pass)
}
```

### Формат блока (lib/prov_crypto.h)

- hex, `nonce(12) | tag(16) | ciphertext`
- AES-256-GCM (mbedtls), ключ — base64 от 32 байт из `espectre_encryption_key`
- открытый текст: `ssid\npassword`

### Поиск сетей (/scan)

- Обработчик `WIFI_EVENT_SCAN_DONE` (`on_scan_done`) забирает записи сразу после события.
- Перед сканированием `esp_wifi_set_mode(WIFI_MODE_APSTA)`, если режим `WIFI_MODE_AP`.
- `esp_wifi_scan_start(&cfg, false)`, ожидание семафора до 10 с.

### Тест приёма с ноутбука

```
python3 make_blob.py "ssid" "password" "BASE64-КЛЮЧ" 192.168.4.11
```

Эндпоинт `POST http://<ip>/prov`, тело — hex-блок. Ожидаемо `HTTP 200`, повтор при закрытом окне отклоняется.
