Обновлено: 2026-10-28 (добавлен этап 12: единая кодовая база, режимы «Простой» и «С удалённым экраном», обновление прошивки из файла; ветка `feature/screen-ui`). Исправлена причина потери STA-настроек после сброса и `404` на `/prov`. Новый тест подтвердил нужный поздний старт: C6 поднял AP в 23:29:54; экран позже увидел её BSSID `CC:8D:A2:F3:E2:B1`, подключился и получил `192.168.4.110`. Последняя попытка очищать setup STA при первом скане без соседа оказалась ошибкой: из-за кратковременного пропуска beacon она запустила цикл очистка → перезагрузка → сохранение STA. Она удалена. Когда обе AP уже работают и MAC выбирает устройство точкой, setup STA очищается без новой перезагрузки. Изменение требует сборки и проверки.

Добавлены веб-статусы роли (мастер/AP, слейв/STA, домашняя сеть) и межустройственной связи через отдельный `/peer_identity`. Проверка выполняется фоновой задачей, результат читается из `/status`; код не собран и не проверен на железе.

По уточнению проверка пары сохраняется и в домашней сети: там используется mDNS, но опрос выполняется раз в 30 секунд. Для setup-ролей AP/STA частота остаётся 5 секунд.

Последние логи: роли определились верно (экран AP, C6 STA), C6 получил `192.168.4.110`. Экран продолжает попытки подключения к старой пустой preference `SSID ""`, из-за перезапуска Wi‑Fi адаптера соединение обрывается, а запросы к `192.168.4.11` получают `Host is unreachable`. После актуальной прошивки надо сбросить сеть на экране и проверить `preference_erase=ok` и отсутствие пустого SSID.

Также обнаружено, что после проверки домашней сети C6 отправлял `/prov` до восстановления setup DHCP IP. `probe::try_connect` теперь ожидает прежнюю сеть и IP до 10 секунд; при неудаче отправка соседу отменяется с отдельным статусом.

Последние логи показали, что роль выбиралась лишь единственным сканированием до появления второй AP. В обеих конфигурациях добавлен повторный поиск раз в 10 с до обнаружения соседа/сохранённой сети. Для нераспознанных DHCP клиентов статус-мастер кэширует неудачную проверку по MAC на 15 с, уменьшая повторные HTTP ошибки телефона.

## Требования

- Весы встроены в кафельный пол, питание постоянное.
- Диапазон 1–200 кг.
- Давление > 5 кг (порог срабатывания 1.5 кг) включает дисплей, калибровка, приглашение, ожидание стабилизации, результат.
- Снятие веса: дисплей выключается через 10 с.
- Экран показывает вес, данные сети, статус связи с весами.
- Устройства равнозначны: настроил одно, настроились оба.
- Настройка сети через веб-страницу устройства: поиск сетей, ввод пароля, проверка подключения, отправка соседу.
- Креды по воздуху шифруются AES-256-GCM, ключ = `espectre_encryption_key` (тот же, что для API и OTA).
- Общая сеть настройки `prov_ssid`: ненастроенное устройство сначала ищет сохранённую домашнюю сеть, затем сеть настройки. Не нашло — поднимает сеть настройки как точку доступа.
- Доступ к устройству по IP и по `<имя>.local`.
- Веб-страница на русском, мобильная.

## Правила проекта

1. **Имена** (`id`, `name`, `friendly_name`, ключи substitutions, имена файлов): только латиница, цифры и `_`, без пробелов. Пример: `current_weight`.
2. **Русский** — в текстах, которые видит пользователь (страница, сообщения статуса).
3. **Секреты** — только в `secrets.yaml`, в чат не публикуются.
4. **Окно настройки** — приём кредов только в открытом окне. Счётчика версий нет.
5. **Файлы** — конфиги устройств в `/config/esphome/`, заголовки в `lib/`. Веб-морда встроена в `lib/ui_server.h`, отдельной статики (`web/`) нет.
6. **Межзадачный обмен**: httpd и цикл ESPHome не трогают состояние друг друга напрямую. Команды ставятся в очередь (`cmd_pending`), статус хранится в фиксированном буфере.

**Решения пользователя (2026-10-28):**
- Для разных плат остаются разные YAML-файлы со своими настройками (плата, пины); логика общая (`lib/*.h` и общие пакеты YAML). Бинарник у разных плат разный, у одинаковых плат один.

- Прошивки собираются под разные профили железа, но работают вместе: разные платы друг с другом и одинаковые.
- Дисплей выберем позже (этап 10), в плане он остаётся заглушкой.

**Что надо учесть (найдено при анализе):**
1. Имя `esphome.name` задано при сборке (`floor-scale.local`, `floor-screen.local`), а роль будет меняться в настройках. Поиск соседа по имени хоста перестанет работать. Заменить на поиск по mDNS-сервису (например `_floorscale._tcp` с полем роли в TXT) и проверке `/peer_identity`, либо дать устройствам нейтральные имена по плате.
2. Адреса точек доступа сейчас разные (`192.168.4.10` у весов, `192.168.4.11` у экрана) и зашиты в YAML. В сети настройки точкой в каждый момент является одно устройство, поэтому можно взять один общий адрес точки для всех плат; клиент всегда обращается к нему. Это упрощает одинаковые платы.
3. `device_kind` сейчас переменная времени выполнения, но задаётся из YAML. Придётся читать её из NVS до старта HTTP-сервера и фоновых задач. Задачи `peer_data_task` и прокси калибровки запускаются по роли.
4. Компоненты HX711 и дисплея компилируются в прошивку целиком. Роль управляет ими в рантайме (роль «экран» не опрашивает HX711, `hx711` без датчика шумит предупреждениями). Профиль прошивки определяет, какие роли ей доступны; страница узнаёт это из `/status` (поле возможностей).
5. Определение весов по HX711: датчик без данных держит DOUT высоким, без датчика линия «плавает» (с подтяжкой к земле остаётся низкой). Сделать эвристику по нескольким замерам, результат считать подсказкой для роли, а не автоматическим переключением. Надёжность проверить на железе отдельным тестом на странице «Тесты».
6. Версия протокола: добавить поле `proto` в `/peer_identity` и `/status`, чтобы устройства с разными версиями прошивки понимали друг друга и показывали предупреждение, а не тихо ломались.
7. Конфликт ролей (оба «весы» или оба «экран»): проверка связи показывает отдельное предупреждение. Назначение роли второму устройству можно передавать по зашифрованному каналу так же, как сеть.
8. В режиме «Простой» парная логика не нужна: нет выбора роли по MAC, передачи сети соседу и проверки связи. Нужна только настройка своей Wi-Fi через собственную точку, поэтому `/connect` не должен требовать соседа (сейчас без соседа отвечает ошибкой).
9. Размер прошивки: на 4 МБ флеш две OTA-области; добавление дисплея и графики может не поместиться. Проверить схему разделов перед этапом 10.

- Файл: образ для OTA, а не «factory»/полный образ с загрузчиком. Страница проверяет расширение и размер; после записи проверка образа делается самим ESPHome (`end()`), загрузка нового образа происходит только после успеха.
- Защита от прошивки чужой платой: страница показывает платформу устройства; проверить `chip_id` из заголовка образа.
- Безопасность: ключ `espectre_encryption_key` в `ota: platform: esphome` защищает только родной OTA-протокол ESPHome (прошивка из панели), а не загрузку со страницы. Открытая загрузка прошивки по HTTP означает, что любой в сети может прошить устройство. Варианты защиты: (а) разрешать загрузку только при открытом «окне обновления» (5 минут, как окно настройки); (б) пароль обновления из `secrets.yaml`, вводится на странице (по HTTP передаётся открыто); (в) подпись образа (в ESPHome есть проверка подписи OTA, `USE_OTA_SIGNED_VERIFICATION_MULTI_KEY`; параметры конфигурации надо проверить в исходниках). Окно настройки открывается со страницы без пароля, поэтому как защита от сети оно не работает, только как страховка от случайного нажатия. Рекомендация Claude: обязательный пароль обновления (б), окно (а) как страховка; вариант «вызов-ответ» с тем же ключом (HMAC на JavaScript, ключ по сети не передаётся, но его надо вставить на странице) и подпись образа (в) отдельным шагом. РЕШЕНО 2026-10-28: защита обновления пока не нужна, загрузка файла делается без пароля. Позже добавить пароль, генерируемый из MAC устройства. Замечание Claude: MAC виден в эфире (его знает любой рядом), поэтому пароль только из MAC защиты не даёт; считать его как усечённый HMAC от MAC с ключом `espectre_encryption_key` и показывать на странице только после открытия окна настройки или на экране устройства. В первой версии на страницу выводить предупреждение «обновление не защищено».
- Во время записи HTTP-сервер занят загрузкой; страница показывает прогресс, после перезагрузки сама ждёт возвращения устройства. Обновление второго устройства делается отдельно (проксирование загрузки пока не планируется).
- Тесты: «Проверка обновления» на странице «Тесты» (свободное место, платформа, версия, открыто ли окно обновления) без записи.

## Журнал ошибок и правил работы
- 2026-10-25: DHCP-клиенты мастера (телефон) опрашивались каждые 15 с, давая `select() timeout` в журнале. Теперь не чаще раза в 10 мин (`kNonPeerRecheckMs`). Ошибочная запись в снимке о опросе `192.168.4.11` относилась к тесту «проверка соседа», а не к фоновому монитору.
- 2026-10-25 (регрессия исправлена): кэш «не сосед» на 10 мин блокировал переподключившегося соседа (его проверка в момент перезагрузки падала). Теперь кэш не действует после нового подключения клиента (`netrole::ap_join_ms`). Итог тай-брейка на экране показал `связь с соседом=нет` из-за этого.

- Имена: `name` в REST-адресе становится URL, поэтому латиница без пробелов. Русский только в текстах сообщений и на странице.
- Стек `httpd` 12 КБ (4 КБ переполнялись при сканировании).
- `esp_http_server` подключается через `framework: advanced: include_builtin_idf_components` (в `include_builtin_idf_components` на верхнем уровне `esp32` ESPHome не принимает).
- `wifi_ssid()` в ESPHome 2026.10.0 не существует: имя сети берём через `esp_wifi_sta_get_ap_info`.
- Сканирование: компонент `wifi` ESPHome забирает результаты до нас, поэтому используем обработчик события ESP-IDF.
- Сканирование в режиме только AP даёт `ESP_FAIL`: переключаем в APSTA без подключения.
- `delay()` в `on_boot` блокирует цикл дольше 5 с — срабатывает watchdog. Задержки — только в `script`.
- Два HTTP-сервера не могут делить `ctrl_port`: страница использует `ctrl_port: 32769`.
- Команды калибровки и статус: httpd не трогает состояние ESPHome напрямую (очередь `cmd_pending` + `run_pending()` в цикле датчика).
- Все сетевые заголовки находятся в `lib/` и перечислены в `includes` YAML; после добавления `prov_link.h` нужно обновить ими каталог ESPHome перед сборкой.
- Перед выдачей кода: сверять вызовы ESP-IDF с версией, проверять размеры стеков и буферов, проверять ссылки статическим скриптом (`id`, `ui::`, подстановки, кириллица в именах).

## Проверка пароля без сохранения во флеш

- `probe::try_connect` переключает Wi-Fi storage в `WIFI_STORAGE_RAM`, проверяет сеть и возвращает прежнюю STA-конфигурацию, чтобы передать креды соседу через сеть настройки.
- В используемом ESP-IDF нет `esp_wifi_get_storage`; после проверки явно восстанавливается `WIFI_STORAGE_FLASH` (документированный режим по умолчанию и режим конфигурации проекта).
- Это изменение добавлено в код, поведение на обеих платах нужно проверить вместе со сквозной передачей.

## Известные риски

- **ESPHome 2026.10.0**: не подтверждены `save_wifi_sta`, `clear_sta`, `ap_timeout` (убран), вызовы ESP-IDF для сканирования и проверки, `on_connect` в `wifi`. Ошибки сборки — проверяем по документации версии.
- **AP+STA** — при проверке пароля телефон может потерять связь (канал роутера). Проверено на экране: страница не пропала.
- **Клиентское устройство**: если весы стали клиентом экрана, их страница доступна по IP в сети экрана (адрес в логе). Удобного способа найти её пока нет.
- **Гонка за роль точки** — AP-first и MAC tie-break в `fix/role-selection`; тай-брейк при одновременном старте ещё не проверен на железе.
- **Один ключ** для API, OTA и шифрования кредов. Утечка открывает все три.
- **Пароль на странице** отдаётся в браузер. Для домашней сети приемлемо.
- **Автонуль** на весах сейчас отсутствует (см. этап 0).
- **ESP8266** не рассматриваем: мало памяти, нет аппаратного AES, другой фреймворк.
